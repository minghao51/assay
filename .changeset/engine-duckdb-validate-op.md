feat(m5-2): add the `validate` op — engine execution of compiled m5-1 validation plans (ADR 0040 query lane). `client.validate(handle, plan, overlay?)` executes a `ValidationPlan` against the table's **effective view** (the m4-2 composed base + overlay relation; absent overlay = the plain base view), so an edit/insert/delete that fixes or violates a rule flips that rule's verdict. The plan's SQL is executed byte-identically for cross-surface agreement (m5-4/m5-6): the executor materializes the composed relation under the plan's own binding name, bakes the effective row index into a composer-reserved column (`assay_overlay_ord`), and resolves every reported sample to a **logical row key** (m4-3 grammar) — samples carry row keys + offending values, never bare positions. Result contract per rule: `{ruleId, failCount, failPercent, sampleFailures ≤ min(plan K, engine hard max 100)}`, where `failPercent` is the written integer **half-up** formula `floor((failCount·200 + rowCount) / (2·rowCount))` (0 for an empty dataset) — exact integer arithmetic, portable to the CLI executor; the result carries the effective row count and the total verdict, and per-rule counts must agree with the plan's summary query (the m5-1 no-divergence invariant asserted, not assumed). **Wire hardening (m4-2 precedent)**: the plan is strictly shape-validated at the client and again at the worker boundary — a malformed recognised `engine/validate` request gets exactly one typed `engine/error` before any SQL runs; beyond shape, the executor refuses a binding name that would shadow a registered view and rejects relation tokens outside the compiler's FROM renderings (the second gate against smuggled SQL; compiler SQL itself stays golden-pinned upstream). Sample values are normalized to wire-safe JSON (bigint/hex/exact-decimal text rules) and are report content only — never logged or telemetried (ADR 0025).
