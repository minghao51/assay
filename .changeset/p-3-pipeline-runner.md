feat(p-3): pipeline runner — topological execution of a validated P1 DAG on the real engine. `client.runPipeline(pipeline | compiledPlan, { sources, guard, onNode })` compiles the IR with the pure p-2 `compilePipeline` (or validates a supplied plan), then materializes each node in `plan.order`: source nodes register their dataset through the engine's existing registration path bound to the node's relation, and every other node becomes `CREATE OR REPLACE VIEW "<relation>" AS <sql>` on the query lane (ADR 0040 — pipeline work can never starve the grid's registry-lane windows). ADR 0032 discipline: one explicit user-triggered execution per call — no scheduling, retries, sensors, or run-state persistence; runs are idempotent (a re-run recreates, never appends; source registrations replace their previous view+file); cancellation reuses the generation-guard pattern and reports a typed `canceled` outcome with the named partial state; a mid-DAG failure throws a typed, value-free, node-attributed `PipelineRunError` carrying the already-materialized prefix for inspection and a clean re-run. The p-2 read-only gate holds at the engine boundary: verbatim SQL is classified client-side before any op and re-classified worker-side before any DDL, and relations may never enter the reserved `assay_*` namespace. Wire: two additive typed ops (`engine/pipeline-source`, `engine/pipeline-materialize`) with malformed-request handling and FIFO `OpChannel` discipline; existing ops untouched. Adds the runner-conformance suite to `@assay/testing` (success; mid-DAG failure + clean re-run; cancel; unknown-node refusal; hostile-SQL refusal) and an e2e journey running a 3-node pipeline end-to-end on the real engine.
