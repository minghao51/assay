fix(r1-b): the VS Code webview ships the `eh` DuckDB-WASM pair only, with `wasm_eh` vendored extensions (ADR 0048 decision 3). Electron's Chromium is fixed at 148 and validates the wasm exception-handling probe, so the desktop package no longer carries the legacy `mvp` glue whose missing `_setThrew` bindings masked every DuckDB failure: the committed vendored set is now `duckdb-eh.wasm` + `duckdb-browser-eh.worker.js` (byte-identical to the lockfile package, checksum-pinned by the build) and the Parquet/JSON extensions move to the matching `wasm_eh` autoload paths, so the local-first serve still proves `loaded: true` with zero network fetches. The engine assets shrink: the wasm+glue pair is 5,191,950 B smaller (eh wasm 34,242,586 B vs the mvp 39,362,651 B, plus 71,885 B off the worker), and the whole vendored set goes 43,796,605 → 38,881,030 B (the `wasm_eh` extension builds are slightly larger). Engine failures now reach the user with the engine's own message. The spike harness boots one bundle (the `mvp` boot probe, summary line and invariants are gone; `bundles.eh.*` names the shipped engine) and keeps the non-zero-exit boot-failure drill. No dependency, lockfile or protocol change; the web build's bundle selection and the `wasm_mvp`/`wasm_eh` e2e fixture mapping are unchanged.
