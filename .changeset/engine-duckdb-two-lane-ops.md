feat(m2-7): two-connection op lanes in the engine worker — a long user `query()` (or `profile()` scan) no longer delays the grid's window/metadata traffic. The single T2 FIFO `OpChannel` is split into a query lane (user SQL + profile, heavy scans) and a registry lane (open/schema/range/rowCount/dispose), one DuckDB connection each, so interactive ops issued while a query runs serialize per lane instead of queueing behind it. Measured in e2e (`engine-head-of-line.spec.ts`): an interactive burst behind a ~2.4 s query waited a median of ~2360–2369 ms per op under the single FIFO (~96 % of the query's duration against a ~2–6 ms idle baseline); with two lanes it waits a fixed ~208/511/613 ms (fetchRange/rowCount/schema) that no longer scales with the query's duration, and the query itself is unaffected. T2 guarantees are preserved per lane (single pending query per connection, FIFO order, per-op error isolation — collision-throwing fake-connection tests now cover both lanes), dispose gains a query-lane barrier so in-flight queries settle before views drop, and the wire protocol, client API, and first-batch Arrow transport are unchanged (routing is worker-internal). Also newly exported for consumers: `viewNameForTableId` (the engine-generated `assay_tN` SQL-facing view name for a table id) and the `EngineDatasetProfile` type.
