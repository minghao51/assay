feat(m4-5): the export/rewrite UX over the merged m4-2 export op — pick a format, write a **new file** from the current edited view, and re-open it. The dialog (`export/ExportDialog.tsx`) offers the engine's five formats (Parquet/CSV/JSONL/JSON/Arrow IPC) and states honestly that the engine applies fixed, deterministic options (there are no user-adjustable options in this version). Copy-vs-rewrite is unambiguous (ADR 0012): the notice says it writes a **new file**, that the opened file **is not changed**, and the wording contains no "overwrite"/"in place" language; the current-edited-view row count shown is engine-backed. Result feedback uses the engine's returned `{ format, rowCount, bytes }` verbatim (format + rows + size), and every failure path — engine rejection, OPFS read/write, a save picker that errors rather than being dismissed — surfaces as readable text stating that the opened file is unchanged, leaving the app usable. Destination follows the established picker patterns (mirroring `@assay/data-sources`'s capability vocabulary, implemented in `apps/web`): `showSaveFilePicker` when available (acquired **before** the engine export so the picker stays inside the click's user activation, then written with the OPFS-scratch bytes), otherwise a hidden-anchor download of those same bytes; dismissing the picker is reported as a cancellation with no engine work attempted. `export/scratch.ts` reads the engine's OPFS scratch path (`assay-exports/…`) through `navigator.storage.getDirectory()` (ADR 0017), so the source is never involved. The re-open journey is the normal open flow: the e2e captures the fallback download and reopens it via the filechooser, asserting the edited content returns. **Carry-over closed (m4-4):** decimal leaves nested inside structs/lists no longer render `<16 bytes>` — the parsed type tree from `parseDuckDbType` is threaded through the nested preview (`decimalSpecForParsedType`/`formatDecimalForParsedType`, `nested-preview.ts` `columnType` option), so `payload.geo.lat DECIMAL(21,1)` and `DECIMAL(p,s)[]` elements decode exactly, while a type-unknown or non-decimal 16-byte view keeps its honest binary summary.
