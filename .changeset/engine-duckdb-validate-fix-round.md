fix(m5-2): close the six review items on the engine validate op — three containment gaps, one arithmetic defect, one contract tightening, one privacy leak. **(1) The SQL gate was bypassable**: any non-empty SQL with zero relation occurrences passed the occurrence gate, and a `CREATE TABLE <canary> AS SELECT …` wearing one compiler-shaped FROM occurrence passed it too (a real-browser probe executed `CREATE TABLE review_injected AS SELECT 1` and the canary persisted). Two belts now: the static gate rejects non-`SELECT` statements, multi-statement SQL (statement-boundary scan respecting quoted literals, so rule values containing `;` still parse), and relation-free rule SQL (≥ 1 compiler-shaped FROM occurrence per rule and per summary that has rules; the rule-less plan's empty summary stays the one documented zero-occurrence shape) — and the whole op executes inside a transaction that is ALWAYS rolled back (DuckDB DDL is transactional), so no gate evasion can persist a side effect. **(2) Cleanup destroyed pre-existing user views**: the unconditional `DROP VIEW IF EXISTS <binding>` ran even when this op's `CREATE VIEW` failed on the existing name; the binding view is now dropped only when THIS operation created it. **(3) `failPercentFromCounts` overflowed**: both inputs safe integers while `failCount * 200 + rowCount` was not (`945755921747804 / 9007199254740991` returned 11, exact value 10) — intermediates are now BigInt, pinned at the reviewer pair and at large exact-half boundaries. **(4) The sample bound is now a CLAMP, not a refusal** (superseded in the same release by `engine-duckdb-validate-fix-round-2` — see that entry for the final semantics): the boundary accepted any safe-integer K and the compiled row-samples shape computes `count(*) OVER ()` over every violating row regardless of K. This entry's round-2 mechanism (wire refusal of K > 100) was replaced by the round-3 executor clamp: `SELECT * FROM (<exact rule SQL>) LIMIT min(K, 100)`. **(5) `rowKey` is now a non-empty `string` in the result contract** (was `string | null`): the protocol parser rejects null/empty keys; the loud-failure path for unresolvable keys is unchanged. **(6) Validation failures no longer forward raw engine error text** (DuckDB conversion/binder messages can embed offending values or plan text): every engine-touching step of the op maps to a fixed privacy-safe failure class. The conformance suite pins all of it through the real client (canary probes + catalog-listing absence checks, `review_existing` survival, hard-max acceptance/rejection pair) and under Node against the mirrored fake subject.
