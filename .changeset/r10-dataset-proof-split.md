perf(vscode): stop shipping the D03b test proofs in the production webview bundle (R-10). The six `webview/test-proof/**` modules used to reach the shipped entry through one unconditional `runOpenProofs` call, so they were bundled, shipped and parseable — and yet unreachable, because the gate is a runtime flag, so no bundler could prove them dead. They now live in a second, test-only webview entry (`webview/test-proof/entry.ts` → `dist/webview/dataset-proof.js`), the same shape `dist/e2e-test.cjs` already has for the extension host: the host loads that entry **instead of** the production one, under the predicate it already computes (`ExtensionMode.Test && ASSAY_E2E_EDIT_PROOF === '1'`), and the test-only entry imports the production app at runtime rather than carrying a second copy of it. `webview/dataset.ts` therefore has no import edge to the proofs and esbuild drops all six modules.

Measured with the documented invocation (`pnpm build` with `cwd` `apps/vscode`, from a clean `dist`), on this base: `dist/webview/dataset.js` 1,086,500 → 1,041,801 B raw (−44,699 B, −4.11 %) and 223,689 → 215,464 B gzip (−8,225 B, level 6, as `pnpm measure:bundle` reports it). The proof marker strings (`validation-proof`, `runOpenProofs`, `exerciseRealEditor`/`exerciseStagedDiff`/`exerciseAcceptance`) go from 1 / 2 / 2+2+2 occurrences in `dataset.js` to 0, and appear only in the test-only bundle. Every other bucket is byte-identical (`main.js`, `worker.js`, both test bundles, both vendored DuckDB pins), with one predicted exception: `extension.cjs` grows 57 B because the host now selects the entry. The test-only bundle adds 127,877 B to the packaged payload, where before those proofs were shipped inside `dataset.js`.

The gate is now structural rather than a runtime check on shipped code: production cannot reach the proofs even in principle, since only the test-only bundle installs the proof runner. Gate integrity is unchanged and demonstrated, not assumed — the pinned host e2e (`node apps/vscode/scripts/run-e2e.mjs`, VS Code 1.130.0, offline) still runs the acceptance suite and reports its proof outcomes (`validationProof`, `editProof`, `diffProof`, `acceptanceProof` all true/expected, CLI agreement on all six legs), and re-pointing the test host at the production entry makes that run fail. Production behaviour, copy, the host predicate and the coverage floors (83/76/80/84) are untouched. Only shipped bytes are claimed — no parse/compile or startup saving is measured or implied.
