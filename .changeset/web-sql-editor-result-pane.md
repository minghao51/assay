feat(m2-4): SQL editor + result pane. The app gains a dependency-free SQL surface for the opened table: a textarea editor (Run button or Ctrl/Cmd+Enter) with a Cancel control enabled while a query is in flight, and a result pane that renders one bounded page at a time (50 rows) with previous/next paging, an end-of-results indicator, an empty-result state, and column headers from the Arrow schema. Paging is composed web-side — the user's statement is wrapped as `SELECT * FROM (<statement>) AS _assay_page LIMIT <n> OFFSET <m>` through the existing `query()` op (no wire-level limit/offset); trailing semicolons/whitespace are stripped before wrapping, and multi-statement strings are rejected by the engine with the error surfaced readably. The hint shows both names of the opened table: the app's engine-generated id (`t1`) and the SQL-facing view name (`"assay_t1"`, the engine's documented `assay_` namespace). Cancel is honest UI-level abandonment: the engine worker has no query interrupt, so the abandoned query keeps running worker-side (documented in the pane's cancelled-state text), its late result is discarded via a generation guard and never rendered, and a follow-up run queues behind it on the worker's FIFO and works. Rendering is data-only: SQL text, engine errors, and result cells are untrusted content surfaced through React text interpolation — no HTML/script execution from cells, and no SQL, results, or file names are logged (ADR 0025). Paging math, wrap composition, and the generation guard are extracted as Node-tested pure modules (`paged-query.ts`, `run-guard.ts`).
