feat(p-4): `assay pipeline validate <file>` and `assay pipeline run <file>` — the CLI surface for the Assay Pipeline IR. `validate` loads the IR through the p-1 total parser (malformed documents report located, sanitized errors and exit 2), DAG-validates it, and compiles the p-2 plan — nothing is executed and no source dataset is opened; the human report (or byte-stable `--format json` envelope) lists the plan in topological order with each node's kind, relation, and authored source reference. `run` executes the compiled plan on a local in-memory DuckDB session by binding the p-3 runner's `PipelineRunEngineOps` to a `@duckdb/node-api` connection through the `./node` seam (ADR 0041 — the same `executePipeline` the web client drives, so execution semantics cannot fork), then reports per-node outcomes with row counts and lists the terminal output relations (addressable for inspection/export hosts; they live only in the run's session and end with the process — disclosed in the report). Checkpoint C2 discipline: every source node's dataset is resolved before any execution — relative to the pipeline file's directory, absolute paths pass through — and all resolution failures (non-file kinds, missing/non-string paths, missing/unsupported datasets) are collected, disclosed, and refused at exit 2, never guessed or silently fallen back. Exit classes mirror the validate/diff precedent: 0 success; 1 DAG/compile errors (validate and run) or a typed mid-run node failure with named partial state (run); 2 malformed IR, unreadable file, unresolvable sources, or usage. Every pipeline-derived fragment (node ids, relations, source paths, and `describePipelineError`'s raw YAML excerpts) is sanitized at the rendering boundary — control characters are escaped as visible `\uXXXX` text, so a hostile document cannot inject terminal escapes (the p-2 carry-over). No telemetry.
