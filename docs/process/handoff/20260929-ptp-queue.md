# PT-P Queue — pipeline foundation, stage P1 (p-1…p-5)

> **Arc record (opened 2026-09-29).** Spawned by ruling **D12** (maintainer: PT-P is the first
> post-MVP engineering track; roadmap §7). Stage **P1** per [roadmap §3.2](../../product/03-execution-roadmap.md):
> _pipeline IR schema, DAG validation, source/SQL/transform nodes, DuckDB runner_ — executing
> accepted [ADR 0029](../../adr/0029-sql-first-pipeline-semantics.md) (SQL is the canonical
> transformation target), [ADR 0030](../../adr/0030-owned-pipeline-ir.md) (we own a portable,
> declarative, serializable, engine-neutral, Git-friendly pipeline IR),
> [ADR 0032](../../adr/0032-separate-transformation-dag-from-orchestration.md) (we own the logical
> DAG; scheduling/orchestration stay out — local/manual execution first), within the
> [ADR 0031](../../adr/0031-dbt-sqlmesh-as-compatibility-and-execution-adapters.md) boundary
> (dbt/SQLMesh are adapters, never runtime dependencies — lint-enforced on `packages/pipeline`).
> Companion architecture: [`architecture/02-pipeline-dag-etl.md`](../../architecture/02-pipeline-dag-etl.md).
> P2 (validation/publish nodes, gates, preview, materialization, lineage — ADRs 0033/0035) is a
> follow-on queue, not this one.
>
> **Naming note:** ADR 0030 predates the Assay rename (ADR 0039) — "Data Workbench Pipeline IR"
> in the ADR text means the **Assay Pipeline IR**; no decision change, just the name.

## 2. Ordering, parallelism & conflict rules

1. **p-1 → p-2 → p-3 strictly serialized** (each consumes the previous). p-4 and p-5 are
   parallel-safe against each other after p-3 lands.
2. **p-5 vs ux-6:** both touch the web section layout — serialize or coordinate (see the row).
3. Nothing here may change `DataEngine`/engine contracts beyond additive ops (D13: keep-as-target;
   `packages/engine` is a documented target, not a dependency). Engine changes ride the
   conformance suite like every engine task.

## 3. Standing notes (invariants every task respects)

- **ADR boundaries:** 0029 (SQL canonical target), 0030 (IR properties), 0031 (no dbt/SQLMesh/
  Dagster runtimes — also an AGENTS.md hard rule, lint-enforced), 0032 (no orchestration in the
  core — anything scheduling-shaped is out of scope and gets reported, not built).
- **Purity zones:** `packages/pipeline` model/compile code stays dependency-free and pure (the
  domain/grid purity conventions apply); engine/DOM access only at the runner/web seams.
- **Repo conventions:** byte-stable serialization for anything user-facing or exportable;
  total located-error parsers; value-free error surfaces (ADR 0025 discipline extends to
  pipeline errors — no SQL text, paths, or values in web copy/telemetry-adjacent surfaces);
  injection-safe identifiers via the shared helpers; Conventional Commits; changesets; golden
  fixtures for every shape bug (AGENTS.md).
- **No telemetry** is added by these tasks (`pipeline_run` is reserved in the telemetry design §3.11
  — emitting it is a schema-version decision, not a rider).
- **Scope honesty:** if a task believes P1 needs something P2-shaped (validation/publish nodes,
  materialization policy, lineage), STOP and report — that is a queue-boundary decision.
