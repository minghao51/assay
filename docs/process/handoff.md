## 1. Project identity

**Assay** — _the local-first data workbench_: inspect, validate, compare, repair, transform, and govern structured datasets (Parquet, JSONL, JSON, CSV, Arrow/Feather) in the browser or VS Code, with data never leaving the user's machine by default. Long-term direction: governed data products and an enterprise data control plane.

- **Positioning:** "Understand any dataset before your code does."
- **Stack:** TypeScript · React/Vite · DuckDB-WASM · Apache Arrow · pnpm/Turborepo monorepo.
- **License:** AGPL-3.0-or-later for the open core (ADR 0036).
- **Phase:** pre-MVP (MVP = M0–M6). **M1–M5 complete** (M5 closed 2026-09-20 — exit journey green, exact web≡CLI validation agreement). **M6 (dataset diff — the final MVP milestone) dispatch in progress** — queue signed off 2026-09-20 (maintainer pickup, same pattern as M4/M5); checkpoints C1–C3 resolved at stated defaults (no override); m6-0…m6-4 complete — only m6-5 (the exit journey) remains.

## 4. Environment & tooling (including discovered quirks)

- **Node 24** via nvm; repo pins `.node-version`. **pnpm 11.26.0** comes from corepack via the `packageManager` field — if `pnpm` is not on PATH, prefix commands with `corepack` (e.g., `corepack pnpm install`).
- **pnpm 11 quirks:** build scripts are blocked by default — `allowBuilds: { esbuild: true }` in `pnpm-workspace.yaml` already handles it. After renaming package scopes, always re-run `pnpm install` so workspace links refresh.
- **DuckDB CLI** (v1.5.5 used) regenerates Parquet fixtures: `bash fixtures/parquet/generate.sh` (or `DUCKDB=/path/to/duckdb …`). DuckDB 1.5.x rejects the new lambda syntax — the generator avoids lambdas entirely.
- **Playwright browsers:** `pnpm exec playwright install chromium` once; CI installs its own.
- **No services, no secrets** — local-first; nothing to configure beyond the above.
- **Missing infra (deliberate, tracked):** git hosting **decided 2026-09-16: GitHub** — org/repo creation + first push is a manual action ([manual-actions.md](manual-actions.md) M2; CI never yet run remotely); benchmark harness (O2) landed and hardened (m1-7/T4); a11y CI (O3) not started; demo dataset (O5) approach decided (hybrid), curation not started.

## 5. Definition of done — every change

1. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` green (CI enforces; e2e for web-visible changes).
2. Package changes include a changeset (`pnpm changeset`); product-level narrative changes update root `CHANGELOG.md`.
3. Durable decisions get an ADR (`docs/adr/template.md`, next free number — currently 0042) and a roadmap-backlog update.
4. Dataset-shape bug fixes ship a minimal golden fixture + regression test.
5. Privacy/security rules respected (ADR 0025/0007; see AGENTS.md "Hard rules").

## 6. Task queue — M4: Editing and Transforms (queued 2026-09-18, awaiting maintainer sign-off before dispatch)

M3 (m3-0…m3-5) is complete (§9 aa). M4 delivers (roadmap §3.1 / docs/engineering/04 §6):
**edit overlay, stable row identity, cell edit, insert/delete rows, rename/cast columns,
transformation history, preview, export/rewrite** — exit criteria: _edits are reversible_, and
_Parquet is rewritten rather than incorrectly treated as in-place mutable_ (ADR 0012).

Scoping notes (within ADRs, flagged for sign-off):

- **Row identity mechanism**: ADR 0011 makes identity logical, not file-based. Implementation:
  the overlay layer assigns/derives stable logical row ids (base-row anchor + overlay insert
  sequence), stable across sort/filter/refresh within a session; the strategy module documents
  the boundary (what survives: re-open of the same file version; what doesn't: content changes
  on disk). No new ADR needed unless review surfaces a durable conflict — then stop and report.
- **Editing model**: ops log (typed, ordered, reversible) applied as an overlay in composed SQL
  over the base view — the grid never mutates base data; edits are visible immediately and every
  op is undoable (transaction-like semantics per ADR 0012).
- **Export**: engine gains export/rewrite (COPY-based materialization incl. Parquet rewrite via
  export); **CSV must be formula-injection-safe** (AGENTS security rule — sanitize `=+-@`-leading
  cells on export, documented + probed); export never rewrites the source file in place.
- Carry-overs folded: m3-5's compose-failure alert render pin + DataGrid guard-comment fix (→
  m4-0); inspector freshness revisit at editing (→ m4-3); grid inflight generation-tagging
  (m2-1, → m4-3).

## 7. Multi-agent operating model

This repository is designed to be worked by multiple agent sessions (or humans) without collisions. Three roles; a single agent may play one role per task — **never both implement and approve the same change**.

### 7.1 Roles

| Role                                     | Responsibilities                                                                                                                                             | Must                                                                                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------ |
| **Orchestrator** (1 per session batch)   | Read this handoff + roadmap §3–§5; pick/queue tasks from §6; dispatch to workers; integrate results; update roadmap checkboxes, §2 state table, §9 changelog | own shared files (roadmap, handoff, CHANGELOG, root configs); enforce gates; not write feature code itself                                 |
| **Worker** (N, parallel)                 | Implement exactly **one** task from §6 within its package boundary; run the full gate suite; leave a Conventional Commit + changeset; report evidence        | stay inside the task's package column; not edit shared files (propose instead); not re-decide ledger items; check task-relevant ADRs first |
| **Reviewer** (independent of the worker) | Apply the §7.3 checklist to a completed task; verdict **approve** or **request-changes** (with specific items)                                               | be a different session/agent than the worker; verify by running commands, not by reading diffs alone                                       |

### 7.2 Task protocol (state machine)

```text
claim (orchestrator assigns, marks in-progress)
  → execute (worker: implement + self-verify all gates)
    → review (reviewer: §7.3 checklist; request-changes loops back to worker)
      → integrate (orchestrator: merge/commit, update roadmap + handoff §2/§9, close task)
```

- Claimed/completed state lives in the roadmap checkboxes + commit messages (`feat(m1-2): …` — prefix tasks with their §6 number).
- A task is **not done** until the reviewer approves and the orchestrator integrates.

### 7.3 Reviewer checklist (per task)

- [ ] All gates green with pasted command evidence (`lint/typecheck/test/build`; e2e if web-visible).
- [ ] Conventional Commit; changeset present if any package changed.
- [ ] No new `any` without an explanatory comment; `pnpm format:check` clean.
- [ ] Dependency direction intact: `domain` stays pure (no React/browser/engine imports); no package imports apps; `pipeline` free of dbt/SQLMesh/Dagster runtimes.
- [ ] ADR-conflict scan: nothing contradicts accepted ADRs; any new durable decision comes with a Proposed ADR.
- [ ] Privacy/telemetry: no dataset contents, filenames-where-sensitive, SQL results, or PII in any new telemetry/logging.
- [ ] Tests assert meaningful behavior (no stub-only or trivially-true tests); dataset-shape fixes include a golden fixture + regression test.
- [ ] Docs touched where the change alters described behavior.

### 7.4 Parallelism & conflict rules

- One worker per **package boundary** (the §6 "Package" column) at a time; `web` tasks serialize against anything that touches `grid`/`engine` APIs they consume.
- Shared files (§7.1 orchestrator-owned list) are never edited by workers.
- If a task discovers it must cross its boundary, it stops and reports to the orchestrator, who splits/reassigns.
- **Parallel-batch recipe (proven, m1-5/m1-8 and m1-6/m1-7):** for tasks with disjoint package columns, give each worker its own git worktree on a task branch (`git worktree add -b <task-id> ../<repo>-<task-id> main`); the e2e ports are env-overridable (`ASSAY_E2E_PORT_WEB/ENGINE/DS`, defaults 4173/4179/4180) so only one worktree runs default ports — the other(s) shift (+100). Reviewers verify inside the matching worktree; the orchestrator cherry-picks to `main`, runs the merged gates, then removes worktrees/branches. `DUCKDB=/tmp/duckdb` (v1.5.5) is needed locally for fixture-generating specs.
- When in doubt, serialize — this codebase is small; coordination cost exceeds parallelism gains below task 3.
- **Subagent dispatch mechanics (proven, T-batch):** delegate via the pi subagent extension — `worker` and `reviewer` agents (user scope; both default to `zai/glm-5.3-flash` via the local extension config). **Serialize subagent sessions** — two concurrent glm-5.3-flash sessions hit a provider 429 (§9 i). Write dispatch briefs to `/tmp`, never inside the repo. Worker briefs carry: the §6 task row verbatim + done-when; docs/ADRs to read first; deliverables; explicit pre-authorized boundary exceptions AND forbidden files; the six gates with paste-the-tails evidence (+ port assignment); the block protocol (stop, clean tree, commit nothing, report); a report format. Reviewer briefs carry: the §7.3 checklist adapted to the task, the worker's claims to scrutinize, 'verify by running commands, not diffs alone', read-only discipline, and a final `VERDICT: approve` / `VERDICT: request-changes` line with specific items. Subagent contexts are isolated (no persistent session): a request-changes verdict loops back as a NEW worker dispatch carrying the reviewer's exact required items + the original brief file path, then a fresh reviewer re-verification.

### 7.5 Operating modes (choose per batch of work)

| Mode                                            | When                                                                  | How                                                                                                                           |
| ----------------------------------------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| **Solo** (single agent)                         | Doc-only changes, single small task, maintenance                      | One session does claim→execute, then self-reviews against §7.3 and integrates. Acceptable only for low-risk tasks.            |
| **Orchestrator + workers**                      | Several independent §6 tasks (e.g., 1, 3, 8 in parallel)              | §7.1–§7.4 as written; reviewer duties fold into the orchestrator.                                                             |
| **Orchestrator + workers + reviewer** (default) | Anything touching `engine*`, `grid`, `domain`, or adding dependencies | Full model; reviewer independence is mandatory for these packages.                                                            |
| **Architect escalation**                        | A task would violate or extend an accepted ADR                        | Worker halts; orchestrator spawns an architect pass: Proposed ADR first, decision per contributing.md, then re-plan the task. |
